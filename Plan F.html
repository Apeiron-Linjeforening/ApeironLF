Hvor vi står nå

Sluttmålet: en klonbar mal der hvilken som helst linjeforening kan klone repoet og bygge sin egen nettside kun gjennom admin — gratis, uten server. Squarespace-følelse på statisk git-hosting. Fundamentet for dette er nå på plass.

✓ Ferdig: samlet Admin-senter (Klynge C)

All innholdsredigering bor nå i ett sted: admin.html (Admin-senteret). Det er et skall + moduler: skallet gir meny, oversikt og en modul-vert; hver editor er en tynn modul i admin-modules/<id>.js.

Alle 13 tidligere frittstående *-admin.html-sidene er migrert og slettet: medlemskap, footer, hjelp, oppnåelser, utmerkelser, om-oss, forsiden (index), styret, begrep, oppslag, nyheter, meny, merch.

Slik henger det sammen (viktig for å fortsette):

  • admin.html — skallet. Registeret PANELS[] lister hver modul; «↓ Last ned» + «Se siden» er kontekst-knapper i headeren som kaller den aktive modulens export().
  • admin-common.js — delt: createStore(lsKey, freshFn) (utkast-lager: save/lazySave/reset), esc, enhanceHelp, enableDragSort, saveFile, toast, og registeret AdminPanels.define(id, {title, see, exportName, mount(host, AC)}).
  • En modul sin mount(host, AC) bygger editoren i host og returnerer { export, destroy }. destroy rydder lyttere/modaler ved panelbytte.
  • admin-modules.css — per-modul CSS, klasse-scopet (.mod-meny, .mod-merch …).
  • Full arkitekturbeskrivelse: docs/admin-arkitektur.md.

Redigeringsløkka i dag: rediger i admin → «↓ Last ned» data-fil → commit/push til GitHub → Cloudflare bygger (~1 min). Det er denne nedlasting+commit-følelsen de neste to stegene (G1) fjerner.

Krav som styrer alt under: gratis og uten server. Ingen løpende kostnad, ingen database. Alt skal kunne kjøre som statisk git-hosting (Cloudflare Pages).

G
Nordstjernen — det vi bygger mot nå

Git-CMS & klonbar mal

G1 · Git-basert CMS-følelse

«Lagre» = commit. Ingen nedlasting, ingen manuell push.

Neste store steg Stor

Smerten i dag: «lagre» betyr last-ned-fil + commit + push. Det føles ikke som Squarespace. G1 lar admin committe data-filene direkte til GitHub via GitHubs API + OAuth-innlogging — fortsatt 100 % statisk, fortsatt gratis. Redaktøren ser bare «Lagre → live om et minutt».

Konkret fremgangsmåte
  • Vurder ferdig mønster: Decap CMS (tidl. Netlify CMS) eller TinaCMS sin git-backend — begge er gratis og server-løse. Alternativt et tynt eget lag mot GitHub Contents API.
  • OAuth uten egen server: GitHub OAuth krever normalt en liten token-exchange. Gratis-veier: Cloudflare Pages Functions (samme hosting), eller Decaps innebygde GitHub-backend med en gratis OAuth-proxy.
  • Behold modulenes export() som fallback; legg til en commit()-vei i skallet som skriver samme data-fil via API i stedet for nedlasting.
  • Datamodellen er allerede fil-per-område (*-content.js / *-config.js) — det passer git-CMS godt. Vurder om noen bør bli .json for renere commits.

Avklar først: er styret ok med GitHub-innlogging (OAuth) for redaktører, eller skal innlogging være helt skjult bak noe enklere? Dette avgjør backend-valget.

G2 · Klonbar mal

Enhver forening kloner repoet og bygger sin egen side via admin

Sluttmål Stor

Når innhold, seksjoner og tema alle er data-drevne og redigerbare (F1–F4 under), kan en hvilken som helst forening: klon repo → åpne admin → bygg sin side → publiser.

Forutsetninger (rekkefølge)
  • F1 — all tekst som data (ikke hardkodet i HTML).
  • F2 + F3 — seksjoner av/på og sortering som data → admin kan «+ Ny seksjon».
  • F4 — tema (farger/font/logo) redigerbart i admin (bygger på at sidene allerede bruker CSS-variabler).
  • G1 — «lagre = commit» så ikke-tekniske styrer slipper GitHub helt.
  • Til slutt: en oppsett-veiviser ved første klon (foreningsnavn, farger, logo) som fyller startdataene.

Hvert F-steg gir verdi for Apeiron alene og bygger mot det klonbare produktet — ingen bortkastet innsats.

F
Byggeklossene mot klonbar mal — innholdsarbeid

Fire trinn

F1 · Resterende statisk tekst

Gjør all tekst redigerbar — ikke bare det som endres ofte

Lavest terskel Middels

Tekst som fortsatt er hardkodet i HTML: hero-tittel «Apeiron» og ingress, overskriften «Hva er apeiron?», «Bli medlem»-fordeler, teksten i Fellesskap & samarbeid, Lesesalen, og seksjonsoverskrifter på tvers av sidene.

Fremgangsmåte (ingen ny infrastruktur) Samme mønster som er brukt overalt: flytt teksten ut i content-fila for siden, les den inn ved sideopplasting, og legg feltene til riktig modul i admin-modules/. Bruk createStore + modulens export() — alt fundamentet finnes.

Avgjør først: hvilke tekster er viktigst å få redigerbare i første runde?

F2 · Legg til og fjern seksjoner

Styre hvilke seksjoner som vises på en side

Etter F1 Stor

I dag er antallet seksjoner per side fastlåst i HTML. F2 gjør det mulig å slå seksjoner av/på fra admin — og er det arkitektur-steget som låser opp den klonbare malen (G2).

Teknisk kjerne Hver seksjon registreres i en side-content-fil med et enabled-flagg (og etter hvert en type), og siden rendrer fra den lista i stedet for fast HTML. Dette er det største enkeltsteget — planlegg datamodellen grundig før koding.
F3 · Sorter og flytt seksjoner

Dra for å endre rekkefølgen på seksjoner

Etter F2 Liten

Når F2 gir en seksjonsliste i admin, legger F3 til drag-sortering med AdminCommon.enableDragSort — nøyaktig samme mønster modulene allerede bruker for menypunkter, oppslag og styremedlemmer. Rekkefølgen lagres i content-fila.

F4 · Global designkontroll (tema)

Farger, fonter, logo og spacing fra admin

Muliggjør kloning Stor

En egen Tema-modul: primær-/aksentfarger, fontvalg, logo, avrundinger og spacing-skala. Lagres som CSS-variabler i en egen fil (theme-overrides.css eller theme-config.js) og leses av alle sider. Dette er det som gjør at en annen forening kan få sitt uttrykk uten å røre styles.css.

Forutsetning finnes allerede Sidene bruker i stor grad CSS-variabler (--navy, --gold, --paper …) og fontvariabler. F4 handler om å eksponere disse som redigerbare tokens — gjenbruk gjerne fargekontrollen i palette.js som modulene allerede bruker.

Avklar: ønsker Apeiron faktisk å endre eget uttrykk fra år til år, eller er tema-modulen primært for den klonbare malen?
